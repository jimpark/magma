Overview

Magma is a C++23 library. It gives Basalt applications their windows, their input, and their pixels. Basalt turns a widget tree into paint commands. Magma opens the windows, reads the input, decides when each frame starts, and draws the paint commands.

This guide has these parts. This overview describes what Magma does. The architecture chapter describes how the parts fit together. The getting-started chapter shows a first program. The platform, frame scheduling, and rendering chapters describe each part in detail. The last chapter records benchmark results.

Who this guide is for

This guide is for C++ programmers. You must know C++20 or later and CMake. You must also know the Basalt widget tree and its frame cycle. Read the Basalt guide first if Basalt is new to you. You do not need to know SDL, Blend2D, Metal, Vulkan, or Direct3D.

What Magma does

Magma does these tasks:

  • It creates windows and reports their size, display scale, and refresh rate.
  • It translates operating system input into basalt::event values.
  • It supplies the clipboard, cursors, file dialogs, and text input for input methods.
  • It decides when the next frame can start, from the display’s refresh and from input.
  • It draws Basalt paint commands on the GPU or on the CPU, and shows them in the window.
  • It redraws only the damaged areas of each frame.

What Magma does not do

Magma does not do these tasks. Your application does them.

  • It does not own the event loop. Your application calls Magma from its own loop.
  • It does not keep a widget tree. Your application gives events to Basalt and paint commands to Magma.
  • It does not build an accessibility bridge.
  • It does not load fonts. Basalt’s font_manager loads them.

Magma uses Basalt’s types in its API and does not wrap them. A basalt::event from Magma goes directly to basalt::event_router::dispatch. A basalt::paint_commands value from Basalt goes directly to magma::renderer::render.

Parts

The library has three parts.

Part Header Contents
Platform magma/platform.h Windows, input events, clipboard, cursors, file dialogs, text input, display ticks
Frame scheduler magma/frame_scheduler.h The rules that decide when the next frame starts
Renderer magma/renderer.h Draws paint commands into a window or into memory

The header magma/magma.h includes every public header.

Dependencies

Magma uses SDL 3 for the platform and Blend2D for drawing on the CPU. Both are private dependencies. No public header includes them, and your application does not call them. The graphics APIs are private dependencies too.

Basalt is a public dependency. When you link magma::magma, you also get basalt::basalt.

Requirements

Magma needs CMake 3.25 or later. It needs a C++23 compiler and standard library. The README.md file lists the tested compilers, the build options, and the release archives.

Architecture

Magma has three parts: the platform, the frame scheduler, and the renderer. Your application owns the event loop and connects the parts to a Basalt widget tree. This chapter describes each part and the order in which they run.

Parts and data flow

The platform reads input. Basalt changes the widget tree and records paint commands. The renderer draws the commands. The frame scheduler decides when to start each frame. In the diagram, the orange parts are Magma and the gray parts are Basalt.

Your application does these jobs:

  1. It creates the platform, a window, and a renderer for the window.
  2. It gives each event from the platform to Basalt.
  3. It tells the scheduler about display refreshes, input, and frame requests.
  4. When the scheduler says that a frame is due, it runs Basalt’s frame cycle.
  5. It gives the paint commands and the damaged areas to the renderer.

Coordinates

Magma uses two units. A layout pixel is a window coordinate before the display scale. A device pixel is one pixel of the screen.

Events, window sizes, paint commands, and damage are in layout pixels. These are the same units that Basalt uses. The renderer multiplies by the display scale to get device pixels. platform::pixel_size and renderer::pixel_size give sizes in device pixels.

Platform

A platform owns the windows of the process. Create one platform for each process. Use it only on the main thread. The one exception is wake, which you can call from any thread.

Each window has a window_id. Each event from poll_events is a platform_event. It holds the window ID and a basalt::event. A quit request for the whole application uses window 0.

The platform also gives display ticks. A display tick tells when the display refreshed and when it will refresh again. The frame scheduler uses ticks to start frames at the display’s refreshes.

See Platform for the details.

Frame scheduler

A frame_scheduler decides when the next frame can start. It has no clock. You give it the time on each call. Thus the same rules apply in an event loop and in a test.

The scheduler starts at most one frame for each display refresh. It starts a frame for input at once when the previous frame is on the screen. This keeps the time from a key press to the screen short.

See Frame Scheduling for the rules.

Renderer

A renderer draws basalt::paint_commands into one window, or into memory. It keeps the last frame. On each frame, it draws only the damaged areas and keeps the remaining pixels.

The renderer has four backends: raster on the CPU, and metal, vulkan, and d3d12 on the GPU. All backends give the same image within a small tolerance. The raster backend is the reference.

See Rendering for the backends and their settings.

Event loop

The event loop belongs to your application. Each pass through the loop does these steps:

  1. While a frame is pending, call platform::request_display_tick.
  2. Call platform::wait_for_events with the timeout from frame_scheduler::wait_timeout.
  3. Give each tick from take_display_tick to frame_scheduler::display_refreshed.
  4. When renderer::frame_in_flight is false, call frame_scheduler::frame_shown.
  5. Call poll_events and give each event to Basalt. For input, call request_input_frame.
  6. When frame_due is true, call begin_frame, run Basalt’s frame cycle, and call renderer::render.

The wait ends at a display tick, at an event, at a call to wake, or at the timeout. Thus an idle application uses no processor time.

Threads

Magma is not thread-safe. Call the platform, the scheduler, and the renderer from the main thread. To end a wait from another thread, call platform::wake. Then the loop runs, and your code on the main thread reads the result of the other thread.

The raster backend draws large areas on up to four threads. Blend2D manages these threads. The drawing is complete when render returns.

Errors

Functions that can fail return std::expected. The error types are platform_error and render_error. Each has a message that describes the problem.

A failed render can be temporary. For example, the window can be hidden or in a resize. Mark the tree for repaint and try again on the next frame. Do not stop the program for one failed frame.

Getting Started

This chapter builds a small program in seven steps. The program opens a window with a label and a button. Each click on the button increases the count in the label. The program is the same as examples/hello_window.cpp.

Step 1: Add Magma to your project

Add Magma with CMake FetchContent. Use a release tag as GIT_TAG. The target magma::magma brings basalt::basalt with it.

cmake_minimum_required(VERSION 3.25)
project(hello LANGUAGES CXX)

include(FetchContent)
FetchContent_Declare(magma
  GIT_REPOSITORY https://github.com/nadiasvertex/magma.git
  GIT_TAG v0.6.0)
FetchContent_MakeAvailable(magma)

add_executable(hello main.cpp)
target_link_libraries(hello PRIVATE magma::magma)

Magma can also be used with add_subdirectory or find_package. See README.md for both. The build downloads Basalt, SDL 3, and Blend2D at configure time. On Linux, install the X11 and Wayland development packages first. README.md lists them.

Step 2: Create the platform and the window

Create one platform. Then create a window with the graphics API that preferred_graphics_api gives. The renderer can use the GPU only with that graphics API.

#include "basalt/basalt.h"
#include "magma/magma.h"

auto main() -> int {
  auto created = magma::platform::create();
  if (!created) {
    std::cerr << created.error().message << '\n';
    return EXIT_FAILURE;
  }
  auto platform = std::move(*created);
  auto const window = platform.create_window({
      .graphics = magma::preferred_graphics_api(magma::backend_preference::automatic),
      .title = "Hello, Magma",
      .size = {480, 240},
  });
  if (!window) {
    std::cerr << window.error().message << '\n';
    return EXIT_FAILURE;
  }

The window size is in layout pixels. On a display with a scale of 2, the window has 960 by 480 device pixels.

Step 3: Create the renderer

Create a renderer for the window. The platform must stay alive while the renderer exists.

  auto rendering = magma::renderer::create(platform, *window);
  if (!rendering) {
    std::cerr << rendering.error().message << '\n';
    return EXIT_FAILURE;
  }
  auto renderer = std::move(*rendering);

The default preference is backend_preference::automatic. The renderer uses the GPU when it can, and the CPU when it cannot. renderer.active_backend() tells which backend it uses.

Step 4: Create the widget tree

Load fonts, make a Basalt widget tree, and add widgets. Use the window’s size and display scale. system_dark_mode tells which color scheme the operating system uses.

  auto fonts = basalt::text::font_manager{};
  if (fonts.add_system_fonts() == 0) {
    std::cerr << "No system fonts found\n";
    return EXIT_FAILURE;
  }
  auto const shaper = basalt::text::text_shaper{fonts};

  auto const scheme =
      platform.system_dark_mode() ? basalt::color_scheme::dark : basalt::color_scheme::light;
  auto tree = basalt::widget_tree{basalt::make_theme(scheme)};
  tree.set_text_shaper(&shaper);
  tree.set_viewport(platform.window_size(*window).value_or(basalt::size{480, 240}));
  (void)tree.set_scale({.display = platform.display_scale(*window).value_or(1.0F)});

  auto clicks = 0;
  auto &root = tree.emplace_root<basalt::box>(basalt::axis::vertical);
  root.set_padding(basalt::length_insets::uniform(basalt::fixed(16)));
  root.set_gap(basalt::fixed(8));
  auto &status = root.emplace_child<basalt::label>("Clicks: 0");
  auto &press = root.emplace_child<basalt::button>("Count a click");
  press.set_variant(basalt::button_variant::primary);
  press.set_on_press([&] { status.set_text(std::format("Clicks: {}", ++clicks)); });
  auto router = basalt::event_router{tree};

The router keeps the viewport and the scale up to date after this step. It reads them from the resized and scale_changed window events that the platform sends.

Step 5: Connect the scheduler to the tree

Make a frame_scheduler with the display’s refresh interval. When the tree needs a frame, request one from the scheduler and end the wait for events.

  auto scheduler = magma::frame_scheduler{refresh_interval(platform, *window)};
  tree.set_frame_request_handler([&] {
    scheduler.request_frame();
    platform.wake();
  });

refresh_interval is a small function in the example. It converts display_refresh_rate to nanoseconds, and uses 60 Hz when the system does not report a rate.

Step 6: Draw a frame

Put the frame in a function. It runs Basalt’s frame cycle and gives the result to the renderer.

  auto const run_frame = [&] {
    auto const frame_time = now_ns();
    scheduler.begin_frame(frame_time);
    tree.advance_animations(std::chrono::nanoseconds{frame_time});
    tree.update_layout();
    router.update_hover();
    renderer.set_metrics(tree.viewport(), tree.scale().display);
    auto const damage = tree.take_damage();
    if (damage.empty() && !renderer.needs_full_redraw()) {
      return;
    }
    auto commands = basalt::paint_commands{};
    basalt::paint_tree(tree, commands);
    if (auto const drawn = renderer.render(commands, damage, tree.theme().colors.background_default);
        !drawn) {
      std::cerr << drawn.error().message << '\n';
    }
    tree.collect_garbage();
  };

set_metrics tells the renderer the viewport and the scale. A change of size or scale discards the frame and sets needs_full_redraw. Then render ignores the damage and draws the whole viewport. This is why the function paints the whole tree.

now_ns gives the time on the platform’s event clock, from platform::event_clock_now. Use the same clock for the scheduler, the display ticks, and the events.

Step 7: Run the event loop

The loop waits for events, updates the scheduler, sends events to the tree, and draws frames.

  auto running = true;
  scheduler.request_frame();
  while (running) {
    if (scheduler.pending()) {
      (void)platform.request_display_tick(*window);
    }
    auto const timeout = scheduler.wait_timeout(now_ns());
    platform.wait_for_events(timeout ? std::optional{std::chrono::nanoseconds{*timeout}}
                                     : std::nullopt);
    if (auto const tick = platform.take_display_tick(*window)) {
      scheduler.display_refreshed(tick->time.count(), tick->interval.count());
    }
    if (!renderer.frame_in_flight()) {
      scheduler.frame_shown();
    }
    for (auto const &incoming : platform.poll_events()) {
      if (auto const *const event = std::get_if<basalt::window_event>(&incoming.event)) {
        if (event->action == basalt::window_action::close_requested) {
          running = false;
        } else if (event->action == basalt::window_action::shown ||
                   event->action == basalt::window_action::resized ||
                   event->action == basalt::window_action::scale_changed) {
          if (!scheduler.follows_display()) {
            scheduler.set_interval(refresh_interval(platform, *window));
          }
          renderer.request_full_redraw();
          scheduler.request_frame();
        }
      }
      router.dispatch(incoming.event);
      if (is_input(incoming.event) && scheduler.pending()) {
        scheduler.request_input_frame();
      }
    }
    if (running && scheduler.frame_due(now_ns())) {
      run_frame();
    }
  }
  return EXIT_SUCCESS;
}

These are the important points:

  • Ask for a display tick only while a frame is pending. An idle application gets no ticks and uses no processor time.
  • When the window is shown, resized, or moved to another display, request a full redraw. The window can be on a display with a different refresh rate.
  • When an input event causes a frame, call request_input_frame. Then the frame starts at once if the previous frame is on the screen.

Build and run the program. Click the button. The label shows the number of clicks.

Platform

The platform class connects your application to the operating system. It creates windows, translates input into Basalt events, and supplies the clipboard, cursors, file dialogs, and text input. It also sends display ticks for frame pacing. The header is magma/platform.h.

Create the platform

Call platform::create once, at the start of the program, on the main thread. It returns a platform or a platform_error.

auto created = magma::platform::create();
if (!created) {
  std::cerr << created.error().message << '\n';
  return EXIT_FAILURE;
}
auto platform = std::move(*created);

The platform can move but cannot copy. Keep it alive while windows and renderers exist.

Windows

create_window takes a window_config and returns a window_id.

Field Default Meaning
graphics software The drawing API of the window. It cannot change after the window exists.
title empty The title in the title bar.
size 960 by 640 The size in layout pixels.
resizable true The user can change the size.
high_pixel_density true The window uses the full resolution of a high-density display.

Set graphics to the value from preferred_graphics_api. If you set software, the renderer can use only the raster backend.

These functions read and change a window:

  • window_size gives the size in layout pixels. pixel_size gives the size in device pixels.
  • display_scale gives the number of device pixels for each layout pixel.
  • display_refresh_rate gives the refresh rate in hertz, if the system reports one.
  • window_position and set_window_position use layout pixels on the desktop.
  • set_window_size, set_window_title, and set_fullscreen change the window. set_fullscreen(window, false) returns the window to its earlier size and position.
  • system_dark_mode is true when the operating system uses a dark appearance.
  • destroy_window closes the window.

Functions that read a window return std::nullopt for an unknown window ID.

Events

poll_events returns all queued events as a std::vector<platform_event>. Each item holds the window ID and a basalt::event. Give the event to the event_router of that window’s tree.

The platform makes these Basalt events:

Basalt event Source
window_event Resize, scale change, focus change, close request, shown, and hidden
key_event Key down and key up, with repeat and modifiers
text_input_event Text that the keyboard or an input method commits
ime_event The composition text of an input method, with its selection
pointer_event Mouse movement, buttons, enter, and leave. Touch also makes pointer events.
wheel_event Mouse wheel and trackpad scroll, in layout pixels

A resized window event holds the new viewport. A scale_changed event holds the new display scale. Basalt’s event_router uses these values to update the tree. A close_requested event with window 0 is a quit request for the whole application.

Event times are on the platform’s event clock. platform::event_clock_now gives the current time on that clock. Use it for the frame scheduler too.

Wait for events

wait_for_events blocks until one of these occurs:

  • An event is queued.
  • A display tick arrives.
  • Another thread calls wake.
  • The timeout passes. A timeout of std::nullopt waits with no limit.

The events stay in the queue. Call poll_events after the wait to get them.

wake is the only function that you can call from another thread. Call it when a background task finishes, so that the main loop can read the result.

Display ticks

A display tick tells when the display showed its latest frame, and the time until its next refresh. The frame scheduler uses ticks to start frames at the display’s refreshes.

request_display_tick asks for one tick at the next refresh of the window’s display. The tick ends a wait for events. take_display_tick returns it. Ask again for each tick. If you do not ask, no ticks arrive, so an idle application uses no processor time.

Only macOS 14 and later can send ticks. On other systems, request_display_tick returns false. Then use display_refresh_rate to set the scheduler’s interval. See Frame Scheduling.

Live resize

On some systems, the operating system holds the event loop while the user drags the edge of a window. On macOS, poll_events does not run during the drag. Without a frame, the system stretches the last frame until the drag ends.

set_live_resize_callback sets a function that runs for each resize during the drag. It runs on the main thread, inside the system’s resize loop. Give the event to the tree and draw one frame, then return. The same events also come from the next poll_events. An empty function removes the callback.

platform.set_live_resize_callback([&](magma::platform_event const &resize) {
  router.dispatch(resize.event);
  run_frame();
});

Do not let the callback run while your loop is already in poll_events or in a frame. Use a flag to prevent this. Remove the callback before the objects that it uses are destroyed.

Clipboard and cursors

clipboard_text returns the text on the clipboard. set_clipboard_text replaces it. Both use UTF-8.

set_cursor changes the pointer shape for the application. The shapes are arrow, text, crosshair, pointer, resize_horizontal, resize_vertical, and wait.

File dialogs

show_open_file_dialog and show_save_file_dialog show the system’s file dialog. They return at once. The callback runs when the user closes the dialog.

  • The callback receives std::nullopt when the user cancels the dialog.
  • Otherwise it receives the selected paths.
  • Each file_filter has a name, such as "Images", and a pattern, such as "png;jpg".
  • allow_many lets the user select more than one file in the open dialog.
  • default_location is the first folder or file name that the dialog shows.

If the callback throws an exception, the platform keeps it. The next call to poll_events throws it again.

Basalt widgets that need a file use the tree’s file_dialog. To connect them, set a function with widget_tree::set_file_dialog that calls these platform functions.

Text input

Text fields need text input from the keyboard and from input methods. Call start_text_input for the window to receive text_input_event and ime_event values. Call stop_text_input to stop.

set_text_input_area tells the input method where the text field is, in layout pixels. The input method puts its candidate window near this area. cursor_offset is the caret’s horizontal offset inside the area.

Surfaces for other renderers

The platform also gives the window’s surface to a renderer outside Magma. These functions exist for applications that still use their own renderer. They will become private when Magma’s renderer replaces those renderers.

Function Use
present_pixels Copies premultiplied BGRA pixels to a software window and shows the damaged areas.
metal_layer Gives the CAMetalLayer of a metal window.
vulkan_instance_extensions, create_vulkan_surface, destroy_vulkan_surface Make a Vulkan surface for a vulkan window.
win32_window_handle Gives the HWND of a window on Windows.
create_gl_context, gl_proc_address, swap_gl_buffers Use OpenGL with an opengl window.

Do not use these functions with Magma’s renderer. The renderer uses the surface itself.

Frame Scheduling

The frame_scheduler class decides when the next frame can start. It starts at most one frame for each display refresh, and it starts a frame for input at once when it can. The header is magma/frame_scheduler.h.

Why a scheduler

A frame that starts at a bad time costs time or causes a missed refresh. A frame that starts at a refresh has a full refresh interval to finish. Two frames in one refresh interval waste work, because the display shows only one of them. A frame for a key press that waits for the next refresh adds up to one interval of latency.

The scheduler applies these rules in one place. Your event loop asks it what to do.

Time

The scheduler has no clock. Each function that needs the time takes it as an argument, in nanoseconds. Use platform::event_clock_now, the same clock as the display ticks.

Because the scheduler has no clock, a test can give it any sequence of times. The tests in tests/magma/frame_scheduler_test.cpp do this.

Requests

These functions tell the scheduler that a frame is wanted:

  • request_frame asks for a frame. Use it for animations, for frame requests from the widget tree, and after a resize.
  • request_input_frame asks for a frame because of input. It can start sooner than a frame from request_frame.

Requests combine. Many requests before the next frame cause one frame. pending is true while a request waits.

Signals from the loop

These functions tell the scheduler what happened:

  • display_refreshed(time, interval) reports a display tick. After the first call, follows_display is true. An interval of zero or less keeps the current interval.
  • frame_shown reports that the previous frame is on the screen, or that it drew nothing. Call it when renderer::frame_in_flight is false.
  • begin_frame(now) marks the pending frame as started. A request made during the frame causes another frame.

Questions from the loop

These functions tell the loop what to do:

  • frame_due(now) is true when a frame can start now.
  • wait_timeout(now) gives the time that the loop can wait. std::nullopt means that no frame is pending, so the loop can wait with no limit. Zero means that a frame is due now.
  • next_frame_time() gives the time when the pending frame can start.

Rules

The scheduler starts the pending frame at the first time that one of these rules allows. The rules are in order.

  1. The first frame starts at once.
  2. A frame for input starts at once if the previous frame is on the screen.
  3. With display ticks, a frame starts at the first refresh after the previous frame began.
  4. With display ticks, a frame starts at once if the previous frame is on the screen and began at least one interval ago. Thus the first frame after a pause does not wait for a refresh.
  5. With display ticks, if no tick arrives, a frame starts two intervals after the last refresh. For example, a hidden window gets no ticks. Frames then continue at the interval.
  6. Without display ticks, frames start at least one interval apart.

The default interval is 16,666,667 nanoseconds, which is 60 Hz. Set the real interval in the constructor or with set_interval.

Displays without ticks

Only macOS 14 and later send display ticks. On other systems, request_display_tick returns false. The scheduler then uses only the interval. Set it from display_refresh_rate:

auto refresh_interval(magma::platform const &platform, magma::window_id window) -> std::int64_t {
  auto const rate = platform.display_refresh_rate(window).value_or(60.0F);
  return static_cast<std::int64_t>(std::llround(1e9 / rate));
}

A window can move to a display with a different rate. When a window event arrives and follows_display is false, set the interval again.

Input latency

A frame for input waits for the previous frame to reach the screen. If it did not wait, the new frame would wait inside the GPU driver for the previous one.

On Metal, renderer::frame_in_flight is true until the display shows the frame. On Vulkan and Direct3D 12, it is true until the frame goes to the window system. The raster backend is never in flight.

With display sync on, Metal shows a frame about two refreshes after it starts. See Rendering for the settings that change this, and Benchmarks for the measured latency.

Rendering

The renderer class draws Basalt paint commands and shows the result in a window. It keeps the last frame, so each frame draws only the damaged areas. It has one backend for the CPU and three for the GPU. The header is magma/renderer.h.

Create a renderer

renderer::create(platform, window, preference) makes a renderer for one window. It reads the window’s size and display scale as the first metrics. The platform must outlive the renderer.

renderer::create_offscreen(preference) makes a renderer that draws into memory only. Use it for tests and tools. Call set_metrics before the first frame. The default preference for an offscreen renderer is raster_only, which gives the reference image.

The preference selects the backends that the renderer can use:

Preference Effect
automatic Use a GPU backend when one can start. Otherwise use raster.
raster_only Never create a GPU device.

active_backend tells which backend the renderer uses.

Create the window with preferred_graphics_api(preference). This function gives the graphics API that the preference needs on the current system. A window with the wrong graphics API cannot use the GPU.

Metrics

set_metrics(viewport, scale) sets the viewport in layout pixels and the display scale. The frame has viewport * scale device pixels. Call set_metrics at the start of each frame, with the values from the widget tree.

A change of device size or scale discards the frame and requests a full redraw.

Draw a frame

render(commands, damage, clear) draws one frame and shows it.

  1. It clears each damaged area to the clear color.
  2. It draws the commands, clipped to the damaged areas.
  3. It shows the frame in the window.

The damage rectangles are in layout pixels. Use the result of widget_tree::take_damage. Use the theme’s background color, such as background_default, as clear.

If the damage is empty and no full redraw is pending, render shows nothing. It returns success.

Full redraw

needs_full_redraw is true until the next frame that draws everything. While it is true, render ignores the damage and draws the whole viewport. Then the commands must cover the whole viewport.

auto commands = basalt::paint_commands{};
if (renderer.needs_full_redraw()) {
  basalt::paint_tree(tree, commands);
} else {
  auto bounds = damage.front();
  for (auto const &area : damage) {
    bounds = basalt::bounding_union(bounds, area);
  }
  basalt::paint_tree(tree, commands, bounds);
}

When the damage is small, paint only the bounding box of the damage. Paint one box, not each rectangle separately. If you paint each rectangle separately, a parent’s background can cover what an earlier rectangle drew.

Call request_full_redraw when the window shows again after it was hidden or covered. The system can discard the window’s pixels at these times.

Backends

Backend Device Systems
raster CPU, with Blend2D All
metal GPU, with Metal macOS
vulkan GPU, with Vulkan Linux and Windows
d3d12 GPU, with Direct3D 12 Windows

The raster backend is the reference. The golden images in the tests come from it. It draws large areas on up to four threads and small areas on one thread. It shows the frame with platform::present_pixels.

The GPU backends share one design. Each draws every rectangle, rounded rectangle, stroke, line, glyph, and image as one instanced quad. The shader calculates the coverage of each pixel exactly. Glyphs come from an atlas that Blend2D fills, at quarter-pixel positions. A clip that is not aligned to the axes, and a layer with an opacity, draw into an offscreen texture.

Each GPU backend keeps the frame in an image or texture. It redraws the damaged areas and copies the image into the window.

Before each frame, all backends skip the commands that are outside the damaged areas.

On Windows, preferred_graphics_api gives Direct3D 12 when a Direct3D 12 adapter is available. If not, it gives Vulkan.

Text

All backends draw text from the glyph outlines that Basalt gives with font_face::outline. Thus variable fonts show their correct weight. The renderer does not need its own font engine.

Metal

The Metal layer syncs to the display. The system shows a frame about two refreshes after it starts. Without display sync, key presses reach the screen sooner, but slow scrolling tears. Thus display sync is on by default.

These environment variables change the Metal backend. Set them before you create the renderer.

Variable Effect
MAGMA_METAL_REDRAW=full Draw each frame from nothing into the window. needs_full_redraw is then always true, and read_pixel and read_frame return nothing for a window. The default is retained.
MAGMA_METAL_VSYNC=0 Turn display sync off.
MAGMA_METAL_DRAWABLES The number of drawables, 2 or 3. The default is 3.

These settings are for measurement. Benchmarks gives the results of each one.

The Metal backend compiles its shaders when it starts. The build does not need the Metal toolchain.

Vulkan and Direct3D 12

The Vulkan and Direct3D 12 backends wait for the display. Vulkan uses first-in first-out presentation, and Direct3D 12 uses Present(1, 0). Neither can tell when a frame reaches the screen. They report the time when they gave the frame to the window system.

The Vulkan backend loads the Vulkan library when it starts. The build needs no Vulkan SDK.

A software device is slower than the raster backend. Thus the Vulkan backend refuses a CPU device, and the Direct3D 12 backend refuses WARP. These environment variables change this behavior, and turn on validation:

Variable Effect
MAGMA_VULKAN_ALLOW_SOFTWARE=1 Accept a CPU device, for example Mesa’s lavapipe.
MAGMA_D3D12_ADAPTER=warp Use the WARP software adapter.
MAGMA_VULKAN_VALIDATION=1 Load the Khronos validation layer, if it is installed.
MAGMA_D3D12_VALIDATION=1 Turn on the Direct3D 12 debug layer.

Read pixels

read_pixel(x, y) gives the color of one device pixel in the last frame. read_frame gives a copy of the whole frame as a basalt::raster_image_ptr. Both return nothing before the first frame.

Use these functions with an offscreen renderer in tests. This example draws one rectangle and checks a pixel:

auto renderer = magma::renderer::create_offscreen();
renderer.set_metrics({100, 100}, 1.0F);
auto const commands = basalt::paint_commands{
    basalt::fill_rect_command{{{10, 10}, {20, 20}}, basalt::rgba{240, 88, 11, 255}}};
auto const whole = basalt::rect{{0, 0}, {100, 100}};
if (!renderer.render(commands, {&whole, 1}, basalt::rgba{255, 255, 255, 255})) {
  return EXIT_FAILURE;
}
auto const pixel = renderer.read_pixel(15, 15);

Frame statistics

The renderer can record when each frame reaches the screen.

  • track_presentations(true) starts the record. It is off by default.
  • last_frame gives the number of the last frame that render showed, from 1.
  • take_presentations gives the records since the last call. Each presentation has a frame number and a time on the platform’s event clock. The time is empty when a later frame replaced the frame before the display showed it.
  • frame_in_flight is true while the last frame has not reached the screen. Use it to call frame_scheduler::frame_shown.

The meaning of the time depends on the backend. Metal reports when the display showed the frame. The other backends report when they gave the frame to the window system.

Benchmarks

This file records how fast Magma draws in a real application, and the decisions that the numbers support. The numbers come from med, the MEPSA editor, which can draw with its own Skia renderer or with Magma’s renderer. The latest results show that Magma’s Metal backend is as fast as Skia or faster on every measurement. Display pacing removed most missed frames while scrolling. Keystrokes reach the screen within one refresh only when display sync is off, but then slow scrolling tears, so display sync stays on by default.

Method

  • Computer: MacBook Pro, M2 Max. The window was on a display that reports 60 Hz.
  • Program: med in a release build, window size 1180x780 at scale 2, with the article test2.mepsa.
  • Command: just bench-frames 3 test2.mepsa --renderer <skia|magma> in med. Environment variables select Magma’s Metal settings. Each value in the tables is the median of three runs.
  • Scripts: scroll scrolls at a constant rate, fling sends trackpad flings, and type types a paragraph at 80 ms for each key.
  • A missed refresh is a gap between two presented frames that is longer than one refresh interval, while the script runs. Gaps longer than four intervals are pauses in the script and do not count.
  • Key latency is the time from the key event to the time the display showed the frame with the key. With display sync on, Metal reports the time the display showed the frame. The CPU backends report the time they gave the frame to the window system, so their latency is too low by up to one refresh, and their missed refreshes are not visible.

The baseline before Magma’s display pacing was Skia on Metal with a 60 Hz timer. It missed 11 or 12 refreshes in each scroll run, and its median key latency was about 31 ms.

Decisions

  • Damage strategy: the retained frame stays the default. It missed fewer refreshes while scrolling than the full redraw, and its key latency is the same. MAGMA_METAL_REDRAW=full stays available until the external display is measured.
  • Display pacing: frames follow the display link. Scroll misses fell from about 11 to 1 for Magma and to 3 for Skia.
  • Display sync: with sync on, a frame reaches the screen about two refreshes after it starts. This is the system compositor, not the renderer. Only sync off meets the typing target, but with it slow scrolling in med tears in a window, in waves across the text. Sync stays on by default. MAGMA_METAL_VSYNC=0 turns it off.
  • Drawable count: two drawables gave no clear change in one run, so the default of three stays.

Open Measurements

  • The 120 Hz built-in display and the external display, each with the window on it.
  • A way to meet the typing target with display sync on, for example by starting the frame for a keystroke later in the refresh, or by presenting it at a set time.
  • Key latency includes med’s own work for each key, which grows from about 0.1 ms to about 4 ms as the typed paragraph gets longer.
